# GitHub 협업 규칙

이 문서는 해커톤 동안 GitHub에서 충돌을 줄이고 리뷰 가능한 단위로 일하기 위한 최소 규칙이다. 코드 품질 체크리스트는 [코드 리뷰 체크리스트](../standards/code-review.md)를 기준으로 한다.

## 작업 흐름

GitHub Flow를 사용한다. 저장소에는 장기 브랜치를 `main` 하나만 두고, 모든 작업은 `main`에서 기능별 브랜치를 따서 진행한다.

1. `main`은 항상 실행 가능하고 배포 가능한 상태로 둔다.
2. 모든 작업은 `main`에서 새 브랜치를 만든다.
3. 작업 단위가 보이면 PR을 연다. 빠른 피드백이 필요하면 Draft PR을 먼저 연다.
4. CI가 통과하고 리뷰가 끝나면 스쿼시 머지한다.
5. 머지된 브랜치는 삭제한다.

큰 기능도 브랜치는 하나의 사용자 가치나 버그 단위로 자른다. 여러 사람이 같은 파일을 만질 가능성이 있으면 작업 전에 담당 파일을 팀 채널에 공유한다.

새 작업을 시작할 때 기본 명령:

```bash
git switch main
git pull
git switch -c feat/example-api
```

## 이슈 작성

새 작업은 GitHub 이슈 템플릿 중 하나로 시작한다. 시간이 부족하면 모든 항목을 채우기보다 목표, 할 일, 완료 기준만이라도 남긴다.

- 기능/API 작업: 새 API, 화면 연동 기능, 도메인 기능 구현
- 버그: 재현 가능한 오류, 배포/연동 실패, 예상과 다른 응답
- 일반 작업: 문서, 설정, 배포, 리팩터링, 정리 작업

API 계약이 필요한 기능 이슈는 Method/Path, 요청, 응답, 에러를 먼저 적고 클라이언트와 맞춘 뒤 구현한다.

## 브랜치 이름

브랜치명은 `type/short-description` 형식을 쓴다.

| 종류 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat/auth-login` |
| `fix` | 버그 수정 | `fix/jwt-expiration` |
| `docs` | 문서 변경 | `docs/api-conventions` |
| `chore` | 빌드, 설정, 잡일 | `chore/github-actions` |
| `test` | 테스트 추가/수정 | `test/auth-service` |
| `refactor` | 동작 변경 없는 구조 개선 | `refactor/error-response` |

규칙:

- 영어 소문자, 숫자, 하이픈만 사용한다.
- 한글, 공백, 밑줄은 쓰지 않는다.
- 한 브랜치는 한 기능, 한 버그, 한 문서 묶음만 담당한다.
- 문서 정리처럼 여러 사람이 병렬로 작업하는 경우 `docs/<area>` 형식을 쓴다. 예: `docs/backend-standards`, `docs/client-collaboration`.

## 커밋 메시지

Conventional Commits 1.0.0을 따른다.

```text
<type>[optional scope]: <description>
```

예시:

```text
feat(auth): JWT 로그인 추가
fix(error): 검증 응답에 traceId 포함
docs(api): 페이지네이션 계약 문서화
chore(ci): PR에서 Gradle 테스트 실행
test(auth): 로그인 실패 케이스 추가
```

자주 쓰는 종류:

| 종류 | 의미 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가/수정 |
| `refactor` | 동작 변경 없는 개선 |
| `chore` | 설정, 빌드, 의존성 |

커밋 설명은 한국어로 써도 된다. 대신 제목은 한 줄로 끝내고, API 모양이나 DB 스키마가 바뀌면 PR 본문에 따로 적는다.

## PR 규칙

PR은 작게 만든다. 해커톤 중에는 완벽한 분리보다 빠른 리뷰가 중요하므로, 한 PR은 "한 기능 또는 한 문제"만 다룬다.

PR 본문에는 다음을 남긴다.

- 무엇을 바꿨는지
- API 변경이 있는지
- 웹/모바일 팀이 알아야 할 변경이 있는지
- 어떤 테스트를 통과했는지
- 리뷰어가 집중해서 봐야 할 부분
- 문서 변경이면 어떤 문서가 기준 문서인지

API 변경이 있으면 PR 제목이나 본문에 `API 변경 있음`을 명확히 적고, [API 규칙](../standards/api-conventions.md)의 변경 규칙을 따른다.

## 리뷰 대응 규칙

- 리뷰 코멘트는 수정, 설명, 후속 이슈 중 하나로 닫는다.
- 동의하지 않는 코멘트는 근거를 남기고 대안을 제시한다.
- 단순 오타/문서 링크 수정은 재리뷰를 오래 기다리지 않고 담당자 확인 후 머지할 수 있다.
- API 형식, 인증, DB 스키마, 배포 설정 변경은 최소 1명에게 확인받는다.

## main 브랜치 보호

GitHub 저장소 설정에서 `main`에 다음 규칙을 권장한다.

- 머지 전 PR 필수
- 승인 1명 필수
- 머지 전 status check 통과 필수
- 필수 status check: `CI / 빌드 가능 여부 확인`
- 머지 전 대화 해결 필수
- 선형 히스토리 필수
- 스쿼시 머지 허용
- 강제 푸시 비활성화
- `main` 브랜치 삭제 허용 비활성화

현재 CI는 PR에서 `./gradlew bootJar -x test --no-daemon`으로 빌드 가능 여부를 빠르게 확인한다. 해커톤 중 속도가 너무 느려지면 "승인 1명" 규칙만 잠시 완화한다. 필수 status check는 유지하는 것이 원칙이지만, CI/CD가 아직 안정화되지 않은 단계에서는 로컬 검증 결과를 PR에 남기고 팀 리드가 예외 머지를 결정한다.

## 머지 전략

기본은 스쿼시 머지다. 이유는 짧은 시간에 커밋이 지저분해지기 쉽고, 평가자는 최종 히스토리에서 기능 단위를 읽는 편이 더 쉽기 때문이다.

스쿼시 머지 제목도 Conventional Commits 형식으로 정리한다.

## 충돌 처리 기준

- 충돌 해결 전 `git status`로 내 변경과 다른 사람 변경을 구분한다.
- 다른 사람이 맡은 문서를 임의로 고치거나 되돌리지 않는다.
- 충돌이 API 문서와 구현 중 어느 쪽이 맞는지의 문제라면 Swagger/실제 코드/팀 합의 순서로 확인한다.
- 해결 후에는 관련 파일만 스테이징한다.
