## 1. 요구사항 분석 및 피쳐 리스트업

### 서비스 요약

P!NGO는 사용자가 실제 장소에 접근해야 숨겨진 잼컨을 확인할 수 있는 위치 기반 콘텐츠 수집 서비스입니다.

사용자는 지도 위에서 반경 밖 콘텐츠를 `?` 상태로 확인하고, 반경 안에 진입하면 `!` 상태로 변경된 콘텐츠를 열람할 수 있습니다. 이후 해당 장소에 남겨진 썰을 읽고, 감정 반응을 남기거나 자신의 썰을 추가할 수 있습니다.

핵심 가치는 단순한 장소 리뷰가 아니라, **그 장소에 직접 갔을 때만 느낄 수 있는 사소한 이야기와 웃음, 그리고 오프라인 맥락 기반의 연결감**을 제공하는 것입니다.

---

### 구현 피쳐 리스트

#### 1. 장소 기반 썰 목록 조회

- 특정 장소에 등록된 썰 목록을 조회합니다.
- 최신순, 인기순 정렬을 지원합니다.
- 목록 응답에서는 카드 UI에 필요한 최소 정보만 반환합니다.
  - 스토리 ID
  - 5글자 후킹 키워드
  - 한 줄 미리보기
  - 이미지 정보
  - 내가 누른 반응 타입
- 인기순 정렬은 각 스토리에 달린 전체 반응 수를 기준으로 처리합니다.

#### 2. 썰 상세 조회

- 사용자가 바텀시트의 프리뷰 카드를 탭하면 전문 읽기 화면에 필요한 데이터를 조회합니다.
- 상세 응답에는 다음 정보를 포함합니다.
  - 스토리 제목
  - 스토리 전문
  - 장소 정보
  - 생성 시각
  - 카테고리
  - 반응별 개수
  - 내가 누른 반응
  - 댓글 정보

#### 3. 썰 생성

- 사용자가 “썰 추가하기” 화면에서 카테고리, 후킹 키워드, 상세 내용을 입력하면 스토리를 생성합니다.
- 생성된 썰은 이후 장소별 썰 목록 조회 API를 통해 바텀시트 카드에 반영될 수 있도록 설계했습니다.
- 클라이언트가 작성 완료 후 “내 썰 카드 보러 가기” 플로우로 자연스럽게 이동할 수 있도록 생성 응답에는 생성된 스토리 식별자를 반환하도록 설계했습니다.

#### 4. 반응 처리

- 사용자가 스토리를 읽고 감정 반응을 남길 수 있습니다.
- 반응은 생성, 수정, 삭제를 각각 별도 API로 나누지 않고 하나의 API에서 처리하도록 설계했습니다.
- 같은 유저가 같은 스토리에 중복 반응을 남기지 않도록 `storyId + userId` 조합의 유일성을 고려했습니다.

#### 5. 댓글 처리

- 사용자는 스토리에 의견을 남길 수 있습니다.
- 상세 화면에서 댓글 목록을 확인하고, 입력창을 통해 댓글을 작성하는 플로우를 고려했습니다.
- 댓글은 스토리와 사용자에 종속되는 데이터로 보고, `Story - Comment - User` 관계를 기준으로 설계했습니다.

#### 6. 사용자 / 장소 기본 데이터

- MVP에서는 빠른 시연을 위해 기본 사용자와 기본 장소 데이터를 구성했습니다.
- 현재 기획상 주요 장소는 성수동 카페거리이며, 이후 여러 장소로 확장 가능하도록 `Spot` 도메인을 별도로 분리했습니다.

주요 API는 다음과 같이 구성했습니다.

| 기능 | Method | URI |
| --- | --- | --- |
| 장소별 썰 목록 조회 | GET | `/api/v1/spots/{spotId}/stories` |
| 썰 상세 조회 | GET | `/api/v1/stories/{storyId}` |
| 썰 생성 | POST | `/api/v1/spots/{spotId}/stories` |
| 스토리 반응 처리 | POST | `/api/v1/stories/{storyId}/reactions` |
| 댓글 생성 | POST | `/api/v1/stories/{storyId}/comments` |

---

### ERD 구조도

- ERD Cloud  
  https://www.erdcloud.com/d/PC2nwAeX3AeLFGaHD

주요 엔티티는 다음과 같이 설계했습니다.

| 엔티티 | 역할 |
| --- | --- |
| `User` | 서비스를 사용하는 사용자 |
| `Member` | 로그인 및 인증 확장 가능성을 고려한 회원 정보 |
| `Spot` | 썰이 등록되는 장소 |
| `Story` | 장소에 남겨지는 잼컨 / 썰 |
| `StoryReaction` | 사용자가 스토리에 남긴 감정 반응 |
| `Comment` | 스토리에 달리는 의견 |

주요 관계는 다음과 같습니다.

- `Spot 1 : N Story`
  - 하나의 장소에는 여러 개의 썰이 등록될 수 있습니다.

- `User 1 : N Story`
  - 하나의 사용자는 여러 개의 썰을 작성할 수 있습니다.

- `Story 1 : N Comment`
  - 하나의 썰에는 여러 개의 댓글이 달릴 수 있습니다.

- `User 1 : N Comment`
  - 하나의 사용자는 여러 개의 댓글을 작성할 수 있습니다.

- `Story N : M User`
  - 사용자는 여러 스토리에 반응할 수 있고, 하나의 스토리에는 여러 사용자의 반응이 달릴 수 있습니다.
  - 이를 직접 N:M 관계로 두지 않고 `StoryReaction` 조인 엔티티로 분리했습니다.

### 배포한 인프라 형상

배포 구조는 다음과 같이 구성했습니다.

```text
iOS Client
   ↓ HTTPS Request
Domain
   ↓
EC2
   ↓
Spring Boot Application
   ↓
MySQL
```

배포 환경에서 고려한 내용은 다음과 같습니다.

- API 기본 경로는 `/api/v1`로 통일했습니다.
- Swagger UI를 배포 환경에서 확인할 수 있도록 설정했습니다.
- 도메인과 HTTPS를 적용하여 클라이언트가 배포 서버에 안정적으로 접근할 수 있도록 구성했습니다.
- DB 접속 정보 등 민감한 값은 환경 변수 또는 배포 환경 설정으로 분리했습니다.
- 추후 운영 환경에서는 DB를 외부에 직접 공개하지 않고, 애플리케이션 서버를 통해서만 접근하도록 구성하는 방향을 고려했습니다.

## 3. 아키텍처 설계 고민

### 1. 기능별 패키지 구조 선택

처음에는 `controller`, `service`, `repository`, `domain`처럼 계층별 패키지 구조를 사용할 수도 있었습니다.

하지만 해커톤에서는 기능 단위로 빠르게 개발하고, 각 담당자가 자신이 맡은 도메인을 독립적으로 수정하는 일이 많기 때문에 기능별 패키지 구조를 선택했습니다.

현재 구조는 다음과 같이 기능 단위로 나뉘어 있습니다.

```text
story
 ├─ api
 ├─ application
 ├─ domain
 ├─ dto
 ├─ error
 └─ repository

reaction
 ├─ api
 ├─ application
 ├─ domain
 ├─ dto
 ├─ error
 └─ repository
```

이 구조를 선택한 이유는 다음과 같습니다.

- 기능별 응집도가 높아집니다.
- 담당자별 작업 범위가 명확해집니다.
- 해커톤처럼 시간이 짧은 상황에서 충돌 가능성을 줄일 수 있습니다.
- 추후 기능 확장 시 관련 파일을 한 패키지 안에서 빠르게 찾을 수 있습니다.

---

### 2. Controller / Service / Repository 책임 분리

각 계층의 책임을 다음과 같이 나누었습니다.

| 계층 | 책임 |
| --- | --- |
| Controller | 요청 값 검증, API 문서화, HTTP 응답 상태 관리 |
| Service | 트랜잭션 처리, 비즈니스 로직 처리 |
| Repository | DB 조회 및 저장 |
| Domain | 엔티티 상태와 핵심 도메인 행위 관리 |
| DTO | 요청 / 응답 데이터 전달 |

특히 Service가 너무 많은 역할을 갖지 않도록, 응답 변환은 DTO의 정적 팩토리 메서드로 분리하는 방향을 고려했습니다.

---

### 3. 위치 기반 기능의 책임 분리

P!NGO의 핵심 UX는 사용자가 실제 장소 반경 안에 들어왔을 때 `?`가 `!`로 바뀌고 콘텐츠가 해금되는 것입니다.

이때 서버가 모든 GPS 거리 계산과 실시간 위치 상태를 관리할 수도 있었지만, MVP에서는 다음과 같이 책임을 나누었습니다.

- 클라이언트
  - 사용자의 현재 위치 확인
  - 지도 표시
  - 반경 진입 여부에 따른 `?` / `!` UI 처리

- 서버
  - 장소 정보 제공
  - 장소에 연결된 썰 데이터 제공
  - 썰 상세, 생성, 반응, 댓글 데이터 관리

이렇게 나눈 이유는 다음과 같습니다.

- 실시간 위치 변화는 클라이언트에서 처리하는 것이 UX 반응성이 좋습니다.
- 서버는 영속 데이터 관리와 API 응답에 집중할 수 있습니다.
- 해커톤 시간 내에 안정적으로 구현 가능한 범위를 유지할 수 있습니다.

---

### 4. 목록 응답과 상세 응답 분리

바텀시트 목록 화면과 전문 읽기 화면은 필요한 데이터의 양이 다릅니다.

따라서 목록 API와 상세 API를 분리했습니다.

- 목록 API
  - 카드 UI에 필요한 최소 데이터만 반환
  - 여러 개의 스토리를 빠르게 보여주는 데 집중

- 상세 API
  - 전문 내용, 반응 개수, 댓글 정보 등 상세 데이터 반환
  - 특정 스토리 하나를 깊게 보여주는 데 집중

이를 통해 불필요하게 큰 응답을 목록 API에서 내려주지 않도록 설계했습니다.

---

### 5. 인기순 정렬 설계

인기순은 스토리의 전체 반응 수를 기준으로 판단했습니다.

처음에는 각 스토리마다 반응 개수를 개별 조회하는 방식을 생각할 수 있었지만, 이 경우 스토리 수만큼 추가 쿼리가 발생할 수 있습니다.

따라서 반응 수를 집계하는 쿼리를 활용해 인기순 정렬을 처리하는 방향으로 설계했습니다.

## 4. 구현 과정 중 고민 및 해결 과정

### 1. 반응 생성 / 수정 / 삭제를 하나의 API로 묶은 이유

반응 기능은 다음 세 가지 동작을 가집니다.

1. 아직 반응하지 않은 상태에서 누르면 반응 생성
2. 이미 누른 반응과 다른 반응을 누르면 반응 수정
3. 이미 누른 반응을 다시 누르면 반응 삭제

처음에는 RESTful하게 다음처럼 API를 분리하는 방식을 고려했습니다.

```text
POST   /stories/{storyId}/reactions
PATCH  /stories/{storyId}/reactions
DELETE /stories/{storyId}/reactions
```

하지만 클라이언트 입장에서는 사용자가 감정 버튼을 누르는 행위가 하나의 인터랙션입니다.

버튼을 누를 때마다 클라이언트가 현재 서버 상태를 판단해서 생성, 수정, 삭제 API를 각각 다르게 호출하면 클라이언트 로직이 복잡해질 수 있다고 판단했습니다.

그래서 최종적으로는 하나의 API로 통합했습니다.

```text
POST /api/v1/stories/{storyId}/reactions
```

서버는 요청한 `storyId`, `userId`, `reactionType`을 기준으로 현재 반응 상태를 확인한 뒤 다음처럼 처리합니다.

| 기존 상태 | 요청 반응 | 처리 |
| --- | --- | --- |
| 반응 없음 | 특정 반응 | 생성 |
| 같은 반응 있음 | 같은 반응 | 삭제 |
| 다른 반응 있음 | 다른 반응 | 수정 |

이 방식의 장점은 다음과 같습니다.

- 클라이언트 연동이 단순해집니다.
- 사용자의 “반응 버튼 클릭”이라는 UX 흐름과 API가 잘 맞습니다.
- 서버가 반응 상태를 일관되게 판단할 수 있습니다.
- 응답으로 최신 반응 개수와 내 반응 상태를 내려주면 클라이언트가 바로 UI를 갱신할 수 있습니다.

대신 REST 관점에서 생성, 수정, 삭제 의미가 하나의 POST 안에 섞인다는 단점이 있습니다.

하지만 해커톤 MVP에서는 클라이언트 연동 속도와 UX 단순성을 우선하여 하나의 API로 통합했습니다.

### 2. Redis를 어디에 사용할 수 있을지 고민한 부분

Redis 도입 후보는 다음과 같았습니다.

| 사용 후보 | 설명 |
| --- | --- |
| 인기순 썰 목록 캐싱 | 특정 장소의 인기순 목록은 반복 조회될 가능성이 있어 캐싱 후보가 될 수 있습니다. |
| 반응 개수 캐싱 | 반응 개수는 상세 화면과 목록 화면에서 자주 사용되므로 캐싱 후보가 될 수 있습니다. |
| 위치 기반 주변 콘텐츠 조회 | Redis Geospatial 기능을 활용하면 특정 좌표 주변의 장소를 빠르게 찾는 데 사용할 수 있습니다. |
| 요청 제한 | 댓글, 반응 API에 Rate Limiting을 적용할 때 사용할 수 있습니다. |
| 세션 / 토큰 관리 | 인증이 고도화될 경우 토큰 블랙리스트나 세션 저장소로 사용할 수 있습니다. |

하지만 MVP에서는 Redis를 사용하지 않았습니다.

사용하지 않은 이유는 다음과 같습니다.

1. **현재 트래픽 규모에서는 MySQL 조회만으로 충분하다고 판단했습니다.**

   해커톤 MVP 시연 환경에서는 대규모 트래픽보다 기능 완성도와 안정성이 더 중요했습니다.

2. **반응과 댓글은 쓰기 작업이 자주 발생할 수 있어 캐시 무효화가 복잡해질 수 있습니다.**

   반응 수를 Redis에 캐싱하면 반응 생성, 수정, 삭제 시마다 캐시를 갱신하거나 삭제해야 합니다. 이 과정에서 DB와 캐시의 값이 일시적으로 불일치할 수 있습니다.

3. **인기순 데이터는 최신성이 중요합니다.**

   사용자가 방금 누른 반응이 인기순 정렬에 반영되어야 하는데, 캐시 TTL을 길게 잡으면 최신성이 떨어지고 짧게 잡으면 캐시 효율이 낮아집니다.

4. **인프라 복잡도를 줄이는 것이 더 중요했습니다.**

   Redis 컨테이너 또는 별도 Redis 서버를 추가하면 배포, 환경 변수, 네트워크, 장애 지점이 늘어납니다. 제한된 시간 안에서는 MySQL 기반으로 안정적으로 완성하는 것이 더 적절하다고 판단했습니다.

5. **성능 병목이 실제로 확인되지 않았습니다.**

   성능 최적화는 병목을 확인한 뒤 적용하는 것이 좋다고 판단했습니다. 따라서 먼저 쿼리 최적화와 인덱스 설계를 우선했고, Redis는 추후 개선 과제로 남겼습니다.

향후 Redis를 도입한다면 다음 순서가 적절하다고 판단했습니다.

1. 인기순 스토리 목록 캐싱
2. 반응 개수 캐싱
3. 위치 기반 주변 장소 조회
4. Rate Limiting 적용

---

### 3. 반응 중복 방지 설계

같은 사용자가 같은 스토리에 여러 개의 반응을 남기면 반응 개수와 내 반응 상태가 꼬일 수 있습니다.

이를 막기 위해 다음 원칙을 적용했습니다.

- 한 사용자와 한 스토리 사이에는 하나의 반응만 존재할 수 있습니다.
- 사용자가 다른 반응을 누르면 새로 생성하지 않고 기존 반응 타입을 변경합니다.
- 사용자가 같은 반응을 다시 누르면 기존 반응을 삭제합니다.

이를 통해 클라이언트는 항상 `myReactionType` 하나만 기준으로 UI를 표시할 수 있습니다.

---

### 4. 목록 조회 성능 고민

스토리 목록에서는 각 스토리별 반응 수, 댓글 수, 내 반응 상태 등 여러 부가 정보가 필요합니다.

단순하게 구현하면 스토리 목록을 조회한 뒤 각 스토리마다 댓글 수와 반응 수를 따로 조회하게 되어 N+1 문제가 발생할 수 있습니다.

이를 줄이기 위해 다음 방향을 고려했습니다.

- 스토리 목록 조회는 정렬 조건에 따라 Repository 쿼리로 처리
- 댓글 수는 스토리 ID 목록을 기준으로 한 번에 집계
- 반응 수는 스토리 ID 목록을 기준으로 한 번에 집계
- 내 반응 상태도 사용자 ID와 스토리 ID 목록을 기준으로 한 번에 조회

이렇게 해서 목록 API가 불필요하게 많은 쿼리를 발생시키지 않도록 설계했습니다.

---

### 5. 공통 응답과 예외 처리

클라이언트가 성공과 실패를 일관되게 처리할 수 있도록 공통 응답 구조를 사용했습니다.

성공 응답은 다음 형태를 기준으로 구성했습니다.

```json
{
  "success": true,
  "code": "성공 코드",
  "message": "성공 메시지",
  "data": {}
}
```

실패 응답은 다음 형태를 기준으로 구성했습니다.

```json
{
  "success": false,
  "code": "에러 코드",
  "message": "에러 메시지",
  "data": null
}
```

이렇게 설계한 이유는 다음과 같습니다.

- 클라이언트가 HTTP 상태 코드뿐 아니라 서비스 내부 code 값으로도 분기할 수 있습니다.
- 에러 메시지 형식을 통일할 수 있습니다.
- Swagger와 API 명세서에서 응답 구조를 일관되게 설명할 수 있습니다.

### 6. Swagger 문서화

클라이언트와 빠르게 연동하기 위해 Swagger를 적용했습니다.

Swagger에서 확인할 수 있도록 각 API에 다음 내용을 작성했습니다.

- API 요약
- API 설명
- Path Variable 설명
- Query Parameter 설명
- Request Body 예시
- Response Body 예시
- 성공 / 실패 응답 코드

이를 통해 iOS 파트가 Notion 명세와 실제 구현된 API를 함께 확인할 수 있도록 했습니다.

## 6. 추후 개선 사항

### 1. 실제 위치 기반 조회 고도화

현재 MVP에서는 장소 데이터를 기준으로 썰을 조회하는 구조입니다.

추후에는 사용자의 위도, 경도 좌표를 서버로 전달받아 주변 장소를 조회하거나, Redis Geospatial 또는 MySQL Spatial Index를 활용해 거리 기반 조회를 고도화할 수 있습니다.

---

### 2. Redis 도입

트래픽이 증가하거나 인기순 조회가 반복적으로 발생하면 Redis 캐싱을 도입할 수 있습니다.

우선순위는 다음과 같습니다.

1. 장소별 인기순 스토리 목록 캐싱
2. 스토리별 반응 개수 캐싱
3. 주변 장소 조회 캐싱
4. 반응 / 댓글 API Rate Limiting

---

### 3. 인증 / 인가 고도화

현재 MVP에서는 빠른 구현과 시연을 위해 사용자 식별 정보를 단순화했습니다.

추후에는 JWT 기반 인증을 적용해 다음을 개선할 수 있습니다.

- 요청 사용자를 토큰에서 식별
- 다른 사용자의 리소스 수정 방지
- 내 반응, 내 댓글, 내 썰 관리 기능 확장

---

### 4. 장소 확장

현재는 MVP 시연 장소 중심으로 구현했지만, 추후 여러 장소를 등록하고 장소별 썰을 확장할 수 있습니다.

이를 위해 `Spot` 도메인을 별도로 분리했고, `Story`가 `Spot`에 연결되는 구조로 설계했습니다.
